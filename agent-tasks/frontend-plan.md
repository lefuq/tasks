# План реализации фронтенда

Основание: [задание](frontend.md), [спецификация](../development-spec.md), [исходное ТЗ](../04-system-integration.md). Уточнения пользователя от 14 ноября 2026 года включены ниже.

## Контракты и уточнения

- Использовать contracts/backend.openapi.yaml. GET /api/workers возвращает ID и имя существующих воркеров; показывать имя, передавать ID. URL и дата создания не выдаются фронтенду.
- Утеря результата отображается как ошибка с возможностью выбрать воркера и переотправить задание новой операцией с новым ключом. Обычные повторы сохраняют ключ операции на сервере.
- Смена воркера допустима после первой временной ошибки и после исчерпания повторов; доступность действий определяет сервер.
- fail с пустой data является полноценным бизнес-результатом и доступен для принятия.

## Этапы

1. Подготовить React, строгий TypeScript, сборку и маршрутизацию. Разделить app, pages, features и shared без пустых слоёв. До готовности контракта выполнять только независимый каркас, не придумывать DTO и эндпоинты.
2. Подключить типы из OpenAPI и единый слой запросов. Отделить серверный кэш от форм, отменять устаревшие запросы, проверять внешние ошибки, обновлять данные после команд. Повтор пользовательского действия сохраняет ключ, новое действие получает новый. Передавать ожидаемую версию.
3. Реализовать вход, выход, текущего пользователя и службу, обработку истёкшей сессии.
4. Реализовать реестр с фильтром по типу и пагинацией, создание и карточку. Имя 1–100 символов и неизменяемо после создания; описание 0–1000; тип process/research/collect. Редактирование разрешено только по серверным правам и состоянию.
5. Раздельно показывать бизнес-состояние, состояние обмена, оператора, воркера, результат и длительность. Использовать работающий API, не демонстрационный массив. Не показывать неподтверждённый переход как завершённый.
6. Реализовать выбор/смену воркера, отправку, повтор, возврат, принятие, сверку и переотправку при утере результата. Сохранение после возврата работает без изменения полей. После принятия редактирование запрещено.
7. Реализовать историю, проблемы и результаты сверки с объяснением неопределённой доставки. Не добавлять действие «Оставить открытой». Конфликт версии показывать без молчаливого перезаписывания данных.
8. Реализовать скачивание .md без исполнения или вставки содержимого как HTML. UTC переводить в часовой пояс браузера с указанием пояса; processing_time показывать в секундах без преобразования часового пояса.
9. Добавить пустые состояния, загрузку, недоступность API и ошибки полей. Обеспечить подписи, семантические элементы, клавиатуру и отображение состояний не только цветом на ширинах 390–1440 пикселей.
10. Передать бэкенду команды сборки/запуска и настройки API. Подготовить README фронтенда и выполнить совместные сквозные проверки.

## Проверки и готовность

- Компонентные проверки через пользовательские действия: границы полей, роли, доступность действий, сохранение без изменений, повтор действия, конфликт версии, локальное время и скачивание, включая пустой файл fail.
- Настоящий API: создание → назначение → отправка → результат → принятие; возврат → сохранение → новая отправка; утеря результата → выбор воркера → переотправка.
- Проверить клавиатуру, ширины 390 и 1440, TypeScript, сборку и консоль браузера. Заглушки допустимы только в изолированных тестах.
- Итог: frontend/, тесты, документация и отчёт о фактически выполненных проверках. Не изменять чужие контракты, сервер, эмулятор и корневую конфигурацию самостоятельно.
