# Задание агенту: фронтенд

План реализации с согласованными уточнениями: [frontend-plan.md](frontend-plan.md).

Реализуй веб-интерфейс по единой спецификации на React и TypeScript. Архитектура — организация по функциональным областям с разделением API, состояния и представления.

## Обязательные исходные материалы и правила

Прочитай целиком `development-spec.md` и `04-system-integration.md` в корне проекта, а также применимые AGENTS.md. Спецификация остаётся единым источником правил; это задание определяет ответственность агента, а не заменяет спеку. Не меняй спеку и не расширяй функциональность. При неоднозначности останови зависимую работу и задай вопрос пользователю. Не отменяй чужие изменения.

Не называй переменные `found`. Не добавляй комментарии и пояснительные docstring в исходники; объяснения помещай в документацию. Не подключайся к существующим БД. Проверки с PostgreSQL выполняй только в отдельном Docker-контейнере, явно задавая его подключение без fallback. Если контейнер не запускается, останови такие проверки и сообщи пользователю. Форматируй только изменённые файлы.

Перед реализацией согласуй с соседними агентами формы контрактов, необходимые для интеграции. Новые бизнес-решения согласуются с пользователем, технические формы уже предусмотренных данных фиксируются в контракте. Не подменяй готовую интеграцию заглушками. В итоговом отчёте перечисли изменения, команды проверок, результаты и оставшиеся ограничения. Непроведённую проверку не называй успешной.

## Границы ответственности

Владеешь `frontend/`, его сборкой, тестами и документацией запуска. Не изменяй сервер, эмулятор, их контракты и корневую конфигурацию запуска самостоятельно. Используй `contracts/backend.openapi.yaml`, подготовленный агентом бэкенда. Передай ему параметры запуска фронтенда для общей конфигурации.

## Архитектура и практики

- Раздели приложение на `app` для сборки приложения и маршрутизации, `pages` для экранов, `features` для сценариев и `shared` для общих UI-элементов и HTTP-инфраструктуры. Не создавай пустые слои и универсальные компоненты без реального повторного применения.
- Включи строгую проверку TypeScript. Типы API выводи из согласованного контракта; не дублируй вручную несовместимые DTO. Обрабатывай внешние ошибки как непроверенный ввод.
- Серверные данные и их кэш отдели от локального состояния формы. Производные значения вычисляй, не храни вторую копию. Состояние держи рядом с потребителем; эффекты используй для синхронизации с внешними системами, а не для цепочек вычислений.
- Используй единый слой запросов с отменой устаревших запросов, обработкой ошибок и обновлением кэша после команд. Не показывай неподтверждённый переход бизнес-состояния как выполненный.
- Повтор одного действия сохраняет ключ идемпотентности, новое действие получает новый ключ. Передавай ожидаемую версию; при конфликте не перезаписывай данные молча.
- Формы и кнопки семантические, поля связаны с подписями, ошибки доступны с клавиатуры и вспомогательным технологиям. Не используй цвет как единственный индикатор состояния.

## Реализация

1. Подключи сборку, маршрутизацию и согласованный контракт API. Если контракт ещё не готов, выполняй независимый каркас; не придумывай поля и эндпоинты.
2. Реализуй демонстрационный вход и выход, текущего пользователя и службу.
3. Реализуй реестр с фильтром по типу и пагинацией, создание, карточку и разрешённое редактирование. Имя 1–100, описание 0–1000 символов; типы строго по спеке.
4. Покажи отдельно бизнес-состояние, обмен, оператора, воркера, результат и длительность исполнения. Отображай серверные данные, не отдельный демонстрационный массив.
5. Реализуй выбор/смену воркера, отправку, повтор, возврат, принятие и запуск сверки в рамках доступных действий. Согласуй с бэкендом получение списка воркеров, не вводи свой справочник.
6. Реализуй историю, проблемы и результат сверки с доступным объяснением неопределённости после потери ответа. Не добавляй кнопку «Оставить открытой».
7. При возврате кнопка «Сохранить» работает и без изменения полей. После принятия редактирования нет. `fail` отображается как бизнес-результат, а не ошибка сети.
8. Скачивай результат как `.md`, не исполняй и не вставляй его содержимое как HTML. Время UTC отображай через часовой пояс браузера с указанием пояса; длительность показывай в секундах.
9. Обеспечь основной сценарий на ширинах 390–1440, пустые состояния, загрузку, недоступность API, ошибки полей, конфликты и истёкшую сессию.

## Проверки и критерии готовности

- Проверки компонентов ориентированы на действия пользователя и доступные названия, а не внутреннее устройство компонентов.
- Проверены формы, границы длин, роли, недоступные действия, сохранение без изменений, конфликт версии, файл и локальное время.
- Сквозной сценарий проходит с работающим API: создание, назначение, отправка, результат, принятие; дополнительно возврат и повторное сохранение.
- Пройдены проверки клавиатурой и на ширинах 390 и 1440. Проверены консоль браузера и сборка TypeScript.
- Заглушки допустимы только в изолированных тестах и не используются вместо API в готовом приложении.
- README фронтенда содержит команды установки, запуска, сборки и проверок, используемые настройки API.
