# План реализации бэкенда

Основание: [задание](backend.md), [спецификация](../development-spec.md), [исходное ТЗ](../04-system-integration.md). План учитывает уточнения пользователя от 14 ноября 2026 года. При расхождении с первоначальным текстом задания применять согласованные уточнения ниже.

## Согласованные уточнения

- Воркеры хранятся в БД: ID, имя, URL запроса, дата создания. GET /api/workers возвращает только ID и имя; URL и дата — служебные поля.
- GET 404 для ранее сохранённого внешнего ID означает утерю результата. Оператор видит ошибку и может выбрать воркера и переотправить задание. Такая переотправка создаёт новую бизнес-операцию с новым ключом; старая операция и история сохраняются.
- Смена воркера разрешена как после первой временной ошибки, так и после исчерпания повторов. Обычный повтор временной ошибки сохраняет прежний ключ.
- Потеря ответа после исполнения моделируется на GET готового результата.
- Разрешён тестовый механизм обработчика для повторной обработки ответа и удержания ответа старой операции до появления новой. Callback не добавляется.
- Эмулятор по умолчанию выдаёт 20% fail с пустой data и 80% success; исход управляется служебной командой. processing_time вычисляется из started_at и finished_at и включает простой.

## Этапы

1. Подготовить сборку и чистую архитектуру: домен, прикладные сценарии и порты, HTTP/фоновые входные адаптеры, PostgreSQL/HTTP выходные адаптеры. Часы, ключи и случайные задержки доступны через порты. Добавить тест архитектурных границ.
2. Подготовить contracts/backend.openapi.yaml для всех API раздела 9 и GET /api/workers: DTO, состояния, доступные действия, ошибки, пагинация, сессия, версии, идемпотентность, файл и восстановление после утери результата. Согласовать контракт с фронтендом; принять контракт эмулятора до реализации обмена.
3. Реализовать миграции сущностей раздела 5 и воркеров, ограничения уникальности и внешние ключи. Реализовать локальный вход, хеширование паролей, защиту сессии и проверки службы, роли, автора и назначения для каждого API, истории и файла.
4. Реализовать создание через «Новое» и сериализованное внутри службы назначение по минимальной нагрузке, затем ID. Возвращённые задания входят в нагрузку, завершённые — нет. Подготовить команду создания оператора с назначением накопленных заданий.
5. Реализовать редактирование, выбор воркера, отправку, возврат, сохранение без изменения полей и принятие success/fail. Проверять версию и состояние. После возврата сохранять прежнего оператора, следующую отправку выполнять с новым ключом. Завершённое задание неизменяемо.
6. Реализовать идемпотентность пользовательских действий и постоянную очередь. Бизнес-изменение, аудит и очередь сохраняются одной транзакцией. Ключ и снимок фиксируются до HTTP; HTTP выполняется вне транзакции. Применение ответа повторно проверяет актуальность операции. Захват очереди ограничен сроком, расписание сохраняется при перезапуске.
7. Реализовать таймауты соединения 3 секунды и запроса 5 секунд; пять повторов после первой попытки с задержками 5/15/30/60/120 секунд плюс случайные 2–5 секунд. Опрос через 10 секунд; 202 не расходует бюджет ошибок. Ручной повтор запускает новый ограниченный цикл. Завершение, возврат и замена активной операции прекращают обычный опрос.
8. Валидировать JSON, ID, status, целую неотрицательную длительность, Base64 и предел декодированного файла 102400 байт. Пустая data при fail допустима. Исключить повторный эффект и применение старого результата; несовпадения сохранять как проблему без молчаливой перезаписи.
9. Реализовать ручную и автоматическую сверку, сохранение обеих сторон и времени, аудит решений. Неизвестный внешний ID восстанавливать POST с прежним ключом, без поиска по ключу. Автоматическая сверка не принимает результат за оператора. Реализовать отдельный сценарий утери результата и новой операции.
10. Совместно с эмулятором подготовить тестовый механизм дубликатов и задержанных ответов с учётом таймаута 5 секунд. Проверить поздний результат после новой операции, в том числе после утери результата.
11. Подключить компоненты к общему запуску по параметрам соседних направлений. Подготовить реальные связанные демонстрационные операции, две службы и шесть заданий по спеке. Добавить README, миграции, команды проверок и нагрузочный профиль. Общий лимит сервера, БД и эмулятора — 2 CPU / 4 ГиБ.

## Проверки и готовность

- Домен и сценарии без Spring; целевые проверки HTTP и безопасности; архитектурные границы.
- PostgreSQL через отдельный Testcontainers: миграции, транзакции, назначения, гонки редактирования/отправки, версии и повтор команд.
- Проверки доступа между службами, чужих заданий и назначений, истории и файла.
- Реальный эмулятор: восстановление очереди и захвата, потеря ответа, смена воркера, один запуск при прежнем ключе, новый запуск после утери результата, дубликаты, старые и невалидные ответы, сверка и исчерпание повторов.
- Нагрузка: 5000 заданий; 20 последовательных клиентов; прогрев 30 секунд, измерения 120 секунд; поровну список с фильтром по типу и страницей 20, карточка, создание и разрешённое изменение. P95 чтения ≤2 секунд, изменения ≤3 секунд; успехи, ошибки, причины и среда отражены в отчёте. Время до внешнего исполнения измеряется отдельно.
- Существующие БД и fallback запрещены. Если тестовый контейнер не запускается, остановить проверки с БД и передать прогон пользователю.
- Итог: исходники backend/, контракт, общий запуск, README, демонабор, нагрузочные сценарии и фактический отчёт о проверках. Не менять исходники соседних направлений.
