# План реализации эмулятора

Основание: [задание](emulator.md), [спецификация](../development-spec.md), [исходное ТЗ](../04-system-integration.md). Уточнения пользователя от 14 ноября 2026 года включены ниже и имеют приоритет над первоначальными формулировками.

## Согласованные уточнения

- По умолчанию случайный исход: 20% fail с пустой data, 80% success. Исход можно задавать служебной командой; он не связывается произвольно с типом задания.
- Потеря ответа после исполнения относится к GET готового результата: результат уже сохранён, ответ теряется. POST не ожидает выполнения.
- Для дубликатов и задержанных результатов разрешён тестовый механизм в обработчике бэкенда. Не добавлять callback-протокол.
- Хранить started_at и finished_at; processing_time — их разница в секундах, включая простой при перезапуске.
- После утери результата приложение переотправляет задание с новым ключом: это отдельная операция и отдельное исполнение. Повтор прежнего ключа не запускает исполнение заново.

## Этапы

1. Подготовить Java/Spring Boot, сборку и миграции. Разделить HTTP, операции и исполнение, PostgreSQL и служебное управление. Часы и задержки отделить для воспроизводимых тестов.
2. Подготовить contracts/emulator.openapi.yaml: публичные POST/GET и служебные операции инспекции, управления исходами и сбоями. Публичный контракт передать бэкенду первым; согласовать команды и параметры готовности.
3. Реализовать независимое постоянное хранилище операций, уникальных ключей, снимков, результатов, счётчиков, времени исполнения и сбоев. Несколько эндпоинтов воркеров используют общий реестр эмулятора; данные приложения не используются.
4. Реализовать атомарный POST /operations с Idempotency-Key и полями name/description/type. Возвращать 202 с ID. Идентичный повтор возвращает прежний ID; изменённое содержимое с прежним ключом — 409. Воркер определяется эндпоинтом, не телом запроса.
5. Реализовать исполнение со случайным интервалом 10–60 секунд в реальном времени. POST быстро подтверждает приём. Не удерживать HTTP или транзакцию на время исполнения. Сохранённые времена и состояние обеспечивают восстановление; повтор не сбрасывает таймер. Счётчик отражает действительные исполнения и не маскирует повторную работу.
6. Реализовать GET /operations/{id}: 404 неизвестной операции, 202 выполняющейся, 200 готовой. Результат содержит ID, success/fail, целую неотрицательную длительность и data. Для success — Base64 Lorem Ipsum до 102400 байт до кодирования; для fail — пустая data. Поиск по ключу не добавлять.
7. Реализовать служебную инспекцию состояния, результата и числа исполнений; настройку исхода; воспроизводимую недоступность, потерю GET-ответа и технически невалидные ответы. Настройки и результаты переживают перезапуск, искусственные сетевые задержки не удерживают транзакции.
8. Совместно с бэкендом реализовать демонстрацию дубликата и удержания старого ответа до новой операции через разрешённый тестовый механизм. Описать доставку в обработчик с учётом таймаута 5 секунд, проверить отсутствие повторного эффекта и замены нового результата старым.
9. Подготовить команды включения, проверки и снятия сбоев, инспекции и возврата обычного режима. Совместно создать реальные внешние операции для демонабора. Передать параметры запуска бэкенду для общего лимита 2 CPU / 4 ГиБ.

## Проверки и готовность

- PostgreSQL в отдельном Testcontainers: конкурентные POST через разные воркеры дают один ID и одно исполнение; конфликт тела даёт 409 без изменения операции.
- Перезапуск и повтор сохраняют ID, результат, таймер и счётчик. Проверить учёт простоя в processing_time.
- Проверить GET 404/202/200, типы, оба исхода, пустую data при fail, Base64 и размер.
- Управляемые часы использовать для быстрых тестов; отдельно проверить реальное ожидание 10–60 секунд и отсутствие перезапуска таймера при повторе.
- Каждый сбой воспроизводится командой и проверяется независимо от приложения. Снятие восстанавливает обычное поведение.
- Совместно проверить потерю ответа, смену воркера с прежним ключом, дубликат, устаревший ответ и новый ключ после утери результата. Счётчик подтверждает одно исполнение на операцию.
- Не подключаться к существующим БД и не использовать fallback. Если Docker-контейнер не запускается, остановить проверки с БД и передать прогон пользователю.
- Итог: emulator/, контракт, команды, тесты, README и фактический отчёт. Не изменять исходники приложения и фронтенда.
