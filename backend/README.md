# Бэкенд системы обмена

Команды в этом документе выполняются из корня репозитория. Описание первоначальной поставки сохранено для технических подробностей; актуальный общий запуск — в [корневом README](../README.md).

Java 21, Spring Boot, PostgreSQL. Сервер реализует жизненный цикл заданий, назначение операторов, локальные сессии, разграничение доступа, постоянную очередь обмена, ограниченные повторы, обработку результатов, проблемы и сверку.

Контракт для фронтенда: [contracts/backend.openapi.yaml](../contracts/backend.openapi.yaml). Исходные критерии `testing/backend/` сохранены без изменений.

Эмулятор реализован отдельным направлением в `emulator/`. Общий Compose запускает сервер приложения, PostgreSQL приложения, эмулятор и его отдельную PostgreSQL. Контракт эмулятора: [contracts/emulator.openapi.yaml](../contracts/emulator.openapi.yaml); команды сбоев и инспекции: [emulator/README.md](../emulator/README.md). Исходники соседнего компонента не изменяются. Фронтенд подключается к опубликованному контракту приложения отдельно.

## Сборка и проверки

Для сборки нужны JDK 21 и Maven 3.9; для интеграционных тестов также запущенный Docker.

```sh
mvn -f backend/pom.xml test
mvn -f backend/pom.xml verify
python3 -m unittest discover -s backend/load -p 'test_*.py'
```

Первая команда запускает unit-тесты и проверку архитектуры без Spring-контекста и БД. Вторая также запускает HTTP-проверки и интеграционные тесты с моками внешней системы. `BackendIT` самостоятельно создаёт одноразовый `postgres:16-alpine`, явно передаёт его JDBC URL, пользователя и пароль через `DynamicPropertySource`, применяет Flyway и удаляет контейнер. Подключения из окружения не используются. При недоступности Docker интеграционный этап завершается ошибкой; другой БД или fallback нет.

Внешний обмен в тестах заменён моками порта `Ports.External`; HTTP-адаптер отдельно проверяется с моком `HttpClient`. Дубликаты и удержанные ответы передаются в тот же метод `ExchangeService.apply`, который вызывает фоновый обработчик. Тесты проверяют фактическую очередь и историю в контейнерной PostgreSQL. Дополнительные HTTP-эндпоинты или callback для этого не добавлены.

Отдельный совместный профиль запускает настоящий jar эмулятора и две одноразовые PostgreSQL. Он проверяет недоступность, потерю готового ответа, смену воркера с тем же ключом, счётчики исполнений, отрицательный результат, дубликат и настоящий удержанный ответ прежней операции:

```sh
mvn -f emulator/pom.xml -DskipTests package
mvn -f backend/pom.xml -Pjoint verify
```

Сетевой ответ полностью получен в пределах 5 секунд и удерживается уже после HTTP. Тестовый повтор получает действующий захват очереди и проходит обычный `ExchangeService.apply`: дубликат доходит до сравнения результата, старый ответ — до проверки активной операции. Проверяются соответствующие записи истории, отсутствие второго бизнес-эффекта и `execution_count=1` по независимой инспекции. Такой повтор существует только в тестовой оснастке, обычный опрос после готового результата не запускается.

Отчёты: `backend/target/surefire-reports`, `backend/target/failsafe-reports`, `backend/target/site/jacoco/index.html`.

Без локальных JDK и Maven можно собрать образ командой:

```sh
docker build -t tz-backend ./backend
```

## Историческая инструкция запуска бэкенда

Для текущего общего запуска пяти компонентов используйте [корневой README](../README.md). Ограничения ресурсов и результаты нагрузки ниже относятся к первоначальному прогону четырёх контейнеров.

## Запуск своего экземпляра

Compose создаёт БД этого проекта в отдельном именованном томе и не публикует порт PostgreSQL. Для тестов эта БД не используется.

```sh
export APP_DB_PASSWORD='local-database-password'
docker compose up -d --build
```

API: `http://localhost:8080`, эмулятор: `http://localhost:8090`. Порты хоста можно изменить через `APP_PORT` и `EMULATOR_PORT`. Готовность: `GET /actuator/health`. Миграции выполняются при запуске. Повторный запуск сохраняет задания, очередь, захваты, расписание, результаты, историю и сессии. Внешние запросы не выполняются внутри транзакций API или применения ответа.

Во время выполнения служебных CLI-команд остановите основной сервер `docker compose stop backend`, а после команды верните его `docker compose start backend`, чтобы дополнительный процесс также помещался в общий бюджет ресурсов. Данные и сессии сохраняются.

Для запуска без Compose обязательны `APP_DB_URL`, `APP_DB_USER`, `APP_DB_PASSWORD`. Не задано ни адреса БД по умолчанию, ни резервного подключения. Для HTTPS задаётся `APP_SECURE_COOKIE=true`. `APP_EXCHANGE_ENABLED=false` отключает только фоновые вызовы эмулятора, не меняя постоянную очередь.

## Пользователи и воркеры

На пустой БД создайте две службы и пользователей. Значения URL ниже замените реальными базовыми URL воркеров, доступными из контейнера бэкенда; сервер добавляет к ним `/operations` и `/operations/{id}`. Воркеры используют общий внешний реестр, как предусмотрено спецификацией.

```sh
export APP_COMMAND_PASSWORD='demo-password'
docker compose run --rm -e APP_EXCHANGE_ENABLED=false backend \
  --server.port=0 --app.command=bootstrap \
  --app.worker-one-url=http://emulator:8090/workers/worker-1 \
  --app.worker-two-url=http://emulator:8090/workers/worker-2
```

`bootstrap` допустим только на пустом справочнике служб; повтор не перезаписывает существующие данные. Пароль передаётся через окружение, хешируется BCrypt и не выводится в журнал.

| Служба | Логин | Роль |
| --- | --- | --- |
| Служба А | initiator1 | Инициатор |
| Служба А | initiator2 | Инициатор |
| Служба А | operator1 | Оператор |
| Служба А | operator2 | Оператор |
| Служба Б | initiator3 | Инициатор |

Во второй службе оператора изначально нет. Общий демонстрационный пароль задаётся `APP_COMMAND_PASSWORD` при инициализации. Выдача API списка воркеров содержит только ID и имя; URL и дата создания остаются служебными.

Полный демонабор из шести заданий создаётся через API приложения и служебный API настоящего эмулятора:

```sh
export DEMO_PASSWORD='demo-password'
python3 backend/scripts/demo.py
```

Команда создаёт новое задание второй службы, ожидающее отправки, успешное и отрицательное ожидающие принятия, возвращённое после невалидного ответа и выполняющееся задание. Реальные POST, результаты и счётчики проверяются независимой инспекцией и сохраняются в `backend/demo-report.json`. После завершения настройки воркеров возвращаются в `normal/random`. Выполняющееся задание затем естественно завершится через 10–60 секунд; снимок демонабора фиксирует его состояние на момент создания.

Для проверки назначения без внешнего обмена можно создать только два исходных задания:

```sh
docker compose run --rm -e APP_EXCHANGE_ENABLED=false backend \
  --server.port=0 --app.command=demo-baseline
```

Это новое задание второй службы и ожидающее отправки задание первой. Не совмещайте эту команду с полным демонабором, если требуется ровно шесть заданий.

Создание оператора второй службы и назначение накопленных новых заданий выполняются одной транзакцией:

```sh
docker compose run --rm -e APP_EXCHANGE_ENABLED=false backend \
  --server.port=0 --app.command=create-operator \
  --app.service-id=2 --app.username=operator3 --app.name=Оператор3
```

При назначении учитываются все незавершённые задания, включая возвращённые; равная нагрузка разрешается по ID. Создание задания и оператора сериализуется блокировкой строки службы. Изменения задания блокируют его строку и проверяют ожидаемую версию. Версия повышается при смене состояния и редактировании карточки; выбор исполнителя, запрос сверки, повтор запроса и новая отправка без смены состояния её не повышают.

Справочник `task_types(code, name)` содержит читаемые названия типов. `GET /api/task-types` возвращает справочник для форм и фильтра, а поле `typeName` в карточке и списках — название текущего типа из БД.

## Использование API

Перед входом вызовите `GET /api/me`. Ответ `401` выдаёт cookie `SESSION` и заголовок `X-CSRF-TOKEN`. Сохраняйте cookie и передавайте этот заголовок во всех изменяющих запросах, включая вход и выход. `POST /api/session` принимает `username` и `password`, меняет ID сессии и возвращает пользователя. Cookie имеет `HttpOnly` и `SameSite=Strict`; сессия хранится в PostgreSQL и истекает после 30 минут бездействия.

Для создания и всех бизнес-команд обязателен `Idempotency-Key`. Один пользовательский шаг использует один ключ при повторах; независимый шаг получает новый ключ. Одинаковый повтор возвращает исходный ответ; другое содержимое с прежним ключом возвращает `409`. Для изменения передавайте `version` из карточки. Идемпотентный повтор обрабатывается до проверки текущей версии.

Карточка отдельно передаёт `state`, `exchange`, `problem`, текущую операцию, результат и серверный список `actions`. Инициатор видит только свои задания; оператор читает задания своей службы и изменяет только назначенные ему. Те же ограничения применяются к истории и файлу. Реестр сортируется по убыванию ID, поддерживает фильтр `type` и страницы с нулевого индекса, размер 1–100, по умолчанию 20.

`send` после возврата и сохранения или после `LOST_RESULT` создаёт новую операцию с новым внешним ключом. `retry` начинает новый ограниченный цикл той же операции с прежним ключом. Смена воркера после временной ошибки также сохраняет ключ. Ключ и снимок задания фиксируются до HTTP; бизнес-изменение, аудит, идемпотентный ответ и очередь сохраняются одной транзакцией.

Ошибки сети, таймауты и `5xx` допускают первую попытку и пять повторов с базами 5/15/30/60/120 секунд и добавкой 2–5 секунд. `202` опрашивается через 10 секунд и не расходует бюджет ошибок. Таймаут соединения — 3 секунды, полного запроса, включая тело, — 5 секунд. Захват очереди действует 30 секунд, просроченный захват можно получить заново. Старый владелец не может изменить очередь или бизнес-состояние. Его поздний ответ остаётся в истории как `discarded_response`.

После неоднозначной доставки выполняется автоматическая сверка. Неизвестный внешний ID восстанавливается повторным POST с тем же ключом; поиска по ключу нет. Обе стороны и время сверки сохраняются в БД и истории. При конфликте валидных результатов исходный результат сохраняется до явного принятия подтверждённого ручной сверкой ответа. Автоматическая сверка не принимает результат и не разрешает принятие противоречащего ответа без ручного подтверждения.

`GET /api/problems` выдаёт задания с открытыми проблемами. Наблюдения, предыдущие операции, попытки, сверки и решения доступны через историю задания. `GET /api/tasks/{id}/result/file` возвращает attachment `.md`, включая пустой файл отрицательного результата; содержимое не исполняется как HTML.

Моменты времени передаются в UTC. `processingTime` в DTO приложения и `processing_time` в контракте эмулятора — длительности в целых секундах. Детальные формы запросов и ответов, ошибки и состояния зафиксированы в OpenAPI.

### Дополнительные уточнения пользователя

- Сверка доступна для завершённого задания; принятый результат остаётся неизменным. При совпадении с ним любой последующей ручной или автоматической сверки проблема закрывается. Оба наблюдения и история сохраняются.
- Если до принятия уже имеется валидный результат, а сверка вернула технически невалидный ответ, доступны возврат инициатору, повтор и новая сверка. Пока ответ не подтверждён, прежний результат не становится автоматически доступным для принятия.
- Невалидное подтверждение POST 202 — проблема контракта доставки: доступны повтор с прежним ключом и сверка, возврат инициатору недоступен. Возврат относится к невалидному готовому результату GET.
- Эмулятор реализуется отдельным направлением. Режим `lost_result` возвращает GET 404 для ранее известного ID; сервер создаёт новую бизнес-операцию и ключ при повторной отправке. Совместный профиль проверяет восстановление и поздний ответ прежней операции.

## Нагрузочный профиль NF08

На отдельном пустом экземпляре сначала выполните `bootstrap`, затем создайте 5000 заданий. `demo-baseline` на этом экземпляре не запускайте. Повтор `load-data` с тем же пользователем и теми же данными не создаёт дубликатов.

```sh
docker compose run --rm -e APP_EXCHANGE_ENABLED=false backend \
  --server.port=0 --app.command=load-data --app.username=initiator1
export LOAD_PASSWORD='demo-password'
export LOAD_OPERATOR_PASSWORD='demo-password'
python3 backend/load/profile.py \
  --environment 'Укажите CPU, RAM, ОС, версии Docker, ограничения компонентов и адрес эмулятора'
```

Генератор использует только стандартную библиотеку Python. Для loopback-адресов системный HTTP-прокси исключается из маршрута. По согласованию пользователя каждый клиент использует одно HTTP keep-alive соединение. Если сервер завершает соединение по протоколу, следующий запрос открывает новое; неуспешный запрос автоматически не повторяется. Он выполняет 30 секунд прогрева и 120 секунд измерений с 20 последовательными клиентами. Каждый клиент циклически выполняет четыре операции с равным весом: список `type=process` с размером 20, карточка, создание и разрешённое изменение собственного задания до отправки. До прогрева готовится по одному заданию на клиента; при создании реестр закономерно растёт. Ошибки входят в замеры и учитываются по причинам. P95 чтения и изменения считаются отдельно. Отчёт содержит все измерения, среду и итоговые счётчики; ненулевые ошибки или превышение порога завершают команду с ошибкой.

После нагрузки отдельная реальная операция отправляется эмулятору с выбором назначенного оператора из `operator1,operator2` и первого настроенного воркера. Отдельно измеряются время до наблюдения готового результата и переданная длительность воркера. Дополнительно инспекция эмулятора возвращает настоящий `finished_at`: в отчёте отдельно указана разница между временем аудита создания и внешним завершением, исходные UTC-моменты и счётчик исполнений. Время наблюдения результата включает задержку опроса бэкенда и не подменяет внешний `finished_at`. Если эмулятор недоступен, проверка внешнего исполнения не объявляется успешной.

Общий Compose ограничивает четыре компонента суммарно 1.75 CPU / 3328 МиБ: сервер 0.75 CPU / 1536 МиБ, его PostgreSQL 0.50 CPU / 1024 МиБ, эмулятор 0.25 CPU / 512 МиБ, PostgreSQL эмулятора 0.25 CPU / 256 МиБ. Это ниже общего предела 2 CPU / 4 ГиБ. Генератор и браузер работают вне этого бюджета. Текущие измерения сохраняются генератором в JSON-отчёт.

## Устройство

- `domain`: сущности, инварианты, переходы и применимость результатов; без Spring, HTTP и хранения.
- `application`: сценарии и порты транзакций, хранилища, часов, генерации ключей, случайных добавок и внешних запросов.
- `adapter/http`: API, транспортные DTO, вход и ошибки.
- `adapter/postgres`: JDBC, постоянные данные и сериализация снимков операций.
- `adapter/worker`: HTTP-клиент и входной планировщик.
- `config`: сборка зависимостей, безопасность и служебные команды.

Flyway создаёт ограничения ключей, внешние ключи, индексы, постоянные сессии, аудит, проблемы, сверки и очередь. Результаты и неизменяемые снимки находятся в документах операций; оба наблюдения конфликтов дополнительно сохраняются в проблемах, попытках и аудите. Автоматический архитектурный тест запрещает зависимости домена и сценариев на внешние слои и связывание HTTP-адаптера с адаптерами БД и эмулятора.
