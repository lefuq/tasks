# Внешний эмулятор

Java 21, Spring Boot 3.5.7, PostgreSQL 17. Публичный и служебный протокол: [OpenAPI](../contracts/emulator.openapi.yaml). Реальные внешние системы не вызываются.

## Запуск

Из каталога `emulator`:

```sh
docker compose up --build -d
sh emulatorctl health
```

Compose создаёт собственную PostgreSQL без публикации её порта. Данные переживают `docker compose restart` и `docker compose down`; `down -v` удаляет данные. Миграция Flyway применяется при запуске. Эмулятор опубликован только на `127.0.0.1:8090`. Служебный API предназначен для локальной демонстрации.

Два эндпоинта воркеров: `http://localhost:8090/workers/worker-1` и `http://localhost:8090/workers/worker-2`. `/operations` использует `EMULATOR_WORKER` (по умолчанию `worker-1`). Именованные эндпоинты используют одну схему и поддерживают любые имена воркеров. Несколько процессов с одинаковым подключением также разделяют реестр. Хранилище приложения не используется.

Для запуска jar: `mvn package`, затем `java -jar target/emulator-1.0.0.jar`. Обязательно явно задать `EMULATOR_DB_URL`, `EMULATOR_DB_USER`, `EMULATOR_DB_PASSWORD` для отдельно подготовленной БД эмулятора; fallback отсутствует. `EMULATOR_PORT` по умолчанию 8090. В рабочем режиме `EMULATOR_EXECUTION_ENABLED=true`; отключение предусмотрено для тестового управления исполнением.

Compose выделяет PostgreSQL эмулятора 0.25 CPU / 256 МиБ, процессу эмулятора 0.25 CPU / 512 МиБ. Остаток общего бюджета 2 CPU / 4 ГиБ — 1.5 CPU / 3328 МиБ для приложения и его БД. Ограничения общей конфигурации должен учитывать бэкенд.

## Протокол и исполнение

POST `/operations` принимает обязательные строковые `name`, `description`, `type` и заголовок `Idempotency-Key`, быстро отвечает 202 с UUID `id`. Имя обрезается по краям и проверяется по C01; описание до 1000 символов, тип `process`, `research` или `collect`. Назначение воркера в теле не принимается. Некорректный JSON/структура — 400, отсутствующие поля/ключ — 422, нарушения значений — 500 `ServerError` согласно C03. Повтор нормализованного снимка с прежним ключом возвращает тот же ID; другой снимок — 409 без изменения записи.

Исполнение эмулятора — ожидание сохранённого срока и формирование Lorem Ipsum. При атомарной регистрации в PostgreSQL выбираются длительность 10–60 секунд и исход (20% fail, 80% success). В той же записи фиксируются `started_at`, `ready_at` и единственный старт исполнения. Конкурентный повтор не изменяет эту запись. Отдельного внешнего побочного эффекта у эмулятора нет. `execution_count=1` фиксирует старт, а не число HTTP-запросов или попыток завершения.

Планировщик каждые 100 мс выбирает готовые операции через `FOR UPDATE SKIP LOCKED` и атомарно сохраняет `finished_at` и результат. Это короткая транзакция; ожидание исполнения не занимает соединение БД и HTTP-поток. Параллельные процессы не завершают одну запись одновременно. После отката незавершённого сохранения формирование чистого результата безопасно повторяется; новое исполнение не регистрируется. После перезапуска продолжается прежний срок. Фактическое завершение учитывает простой и задержку планировщика; `processing_time` не подменяется выбранной длительностью и равен разности целых epoch-секунд завершения и старта (C02).

GET `/operations/{id}` возвращает 404 для неизвестного UUID, 202 до сохранения результата и 200 после. Success содержит Base64 текста Lorem Ipsum, fail — пустую `data`. Декодированный файл не превышает 102400 байт; приложение скачивает его с расширением `.md`. Сохранённые моменты передаются в UTC. Повтор POST или GET не перезапускает таймер. Отдельного поиска по ключу нет.

## Команды

Все команды ниже выполняются из `emulator`. Для другого адреса задайте `EMULATOR_URL`. `configure` заменяет обе настройки целиком. Исход применяется только к новым операциям, сбой — к публичному эндпоинту указанного воркера. Инспекция и health работают независимо от режима доставки.

```sh
sh emulatorctl configure worker-1 normal success
sh emulatorctl configure worker-2 normal fail
printf '%s\n' '{"name":"Demo","description":"","type":"process"}' > /tmp/emulator-request.json
sh emulatorctl submit worker-1 demo-success /tmp/emulator-request.json
sh emulatorctl submit worker-2 demo-fail /tmp/emulator-request.json
sh emulatorctl settings worker-1
sh emulatorctl inspect UUID
sh emulatorctl result worker-1 UUID
```

Вместо `UUID` используйте ID из POST. Инспекция показывает снимок, исходного воркера, состояние, сроки, число исполнений и настоящий результат. Для проверки повторов отправьте тот же файл и ключ через второго воркера: ID и счётчик останутся прежними.

```sh
sh emulatorctl configure worker-1 unavailable random
sh emulatorctl configure worker-1 lose_response random
sh emulatorctl configure worker-1 lost_result random
sh emulatorctl configure worker-1 invalid_json random
sh emulatorctl configure worker-1 unknown_status random
sh emulatorctl configure worker-1 wrong_id random
sh emulatorctl configure worker-1 negative_time random
sh emulatorctl configure worker-1 fractional_time random
sh emulatorctl configure worker-1 invalid_base64 random
sh emulatorctl configure worker-1 oversized_data random
sh emulatorctl reset worker-1
sh emulatorctl reset worker-2
```

Каждую строку `configure` выполняйте отдельно перед проверкой её эффекта. `unavailable` возвращает 503 для POST и GET, но уже начатые исполнения продолжаются. `lost_result` возвращает 404 для публичного GET выбранного воркера, в том числе для уже известного ID выполняющейся или завершённой операции. Запись и результат сохраняются: служебная инспекция и другой воркер доступны, повтор POST с прежним ключом возвращает прежний ID без нового исполнения. Настройка переживает перезапуск; `reset` восстанавливает обычный GET.

Остальные сбои применяются только к GET готового результата. `lose_response` асинхронно удерживает ответ 6 секунд, затем возвращает 504; клиент с общим таймаутом 5 секунд получает сетевой таймаут, не готовый результат. Это моделирование потери ответа посредством превышения таймаута, без разрыва TCP. POST остаётся быстрым. База и HTTP-поток на время удержания не заняты.

Невалидные ответы формируются только при доставке; служебный `inspect` продолжает показывать неизменный корректный результат. Проверяйте сбой через `result`, затем `inspect`, снимайте через `reset` и повторяйте `result`. Перезапуск не снимает настройку. Для потери ответа сначала дождитесь `completed`, включите сбой, запросите результат, повторите POST через другого воркера с прежним ключом и проверьте одинаковый ID/результат и счётчик 1.

## Проверки

```sh
mvn test
mvn verify
```

`test` не обращается к БД или внешним сервисам: доменные правила, сервис исполнения, настройки, искажения ответа, HTTP и управляемые часы проверяются с моками границ. Mockito подключается явно как тестовый JVM-агент.

`verify` дополнительно запускает `EmulatorIT` с отдельным Testcontainers PostgreSQL, двумя реальными HTTP-серверами и Flyway. URL/логин/пароль явно берутся из созданного контейнера через аргументы запуска Spring и перекрывают любое окружение. Проверяются конкурентные приёмы и завершения, ограничения PostgreSQL, конфликт снимка, оба исхода, рестарт процессов, сохранность настроек/результата, таймер при повторе, реальный таймаут 5 секунд и реальное исполнение длительностью 30 секунд. Реальный тест занимает около 30 секунд, остальные используют управляемые часы. При невозможности запуска Docker проверка завершается ошибкой: отключения или перехода к существующей БД нет. Отчёт покрытия: `target/site/jacoco/index.html` после `verify`.

Критерии описаны в [плане проверок](../testing/emulator/TEST_PLAN.md). Совместные сценарии дубликата и задержанного ответа запускаются профилем `joint` бэкенда; команды приведены в [backend/README.md](../backend/README.md). Эмулятор не добавляет callback и не выдаёт сетевую задержку свыше клиентского таймаута за доставленный поздний результат.
