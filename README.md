# Система обмена заданиями

Приложение показывает, как надёжно отправлять задания внешним обработчикам: назначать ответственного оператора, переживать сетевые сбои, повторять доставку без повторного исполнения и разбирать спорные результаты.

Инициатор создаёт задание, оператор выбирает воркер и отправляет его. Внешний эмулятор выполняет операцию за 10–60 секунд и возвращает успешный или отрицательный результат. Оператор проверяет ответ и принимает его; после принятия задание завершено. Если доставка или результат вызывают проблему, доступны предусмотренные состоянием действия: повтор, смена воркера, возврат инициатору и сверка. Состояние задания, состояние обмена и открытая проблема отображаются отдельно.

## Что умеет приложение

- Вход и выход, две роли и разделение доступа по службам. Инициатор видит свои задания, оператор — задания своей службы, изменяет назначенные ему.
- Реестр с фильтром по типу и страницами, создание и редактирование, автоматическое назначение оператору с наименьшей нагрузкой.
- Типы заданий: обработка (`process`), исследование (`research`), сбор (`collect`). Названия хранятся в справочнике `task_types(code, name)` и отображаются на фронте вместо кодов. Имя после обрезки пробелов — 1–100 символов из согласованного алфавита; описание — до 1000 символов.
- Постоянная очередь обмена, ограниченные повторы, восстановление после перезапуска и защита от повторных команд, дубликатов и поздних ответов.
- Просмотр проблем, ручная и автоматическая сверка, история попыток и решений. Противоречащие результаты сохраняются для разбора оператором.
- Скачивание результата как `.md`, включая пустой файл при отрицательном исходе. Время отображается в часовом поясе браузера.

## Компоненты

| Компонент | Назначение | Технологии / каталог |
|---|---|---|
| Фронтенд | Интерфейс инициатора и оператора; Nginx раздаёт статику и передаёт `/api` бэкенду | React, TypeScript, Vite; `frontend/` |
| Бэкенд | API, доступ, назначение, задания, очередь, результаты, сверка и аудит | Java 21, Spring Boot; `backend/` |
| PostgreSQL приложения | Пользователи, задания, сессии, очередь и история | PostgreSQL 16 |
| Эмулятор | Два адреса воркеров с общим реестром операций; реальное ожидание, исходы и управляемые сбои | Java 21, Spring Boot; `emulator/` |
| PostgreSQL эмулятора | Независимые ключи, операции, результаты и настройки сбоев | PostgreSQL 17 |

Браузер обращается к одному адресу фронтенда. Запросы `/api` идут через Nginx в `backend:8080`; cookie сессии и CSRF работают в одном origin. Бэкенд обращается к `http://emulator:8090/workers/worker-1` или `worker-2`. Воркеры используют общую БД эмулятора, независимую от БД приложения. Порты обеих БД на хост не публикуются.

Исходные требования: [спецификация](development-spec.md) и [интеграционное задание](04-system-integration.md). Контракты: [API приложения](contracts/backend.openapi.yaml), [API эмулятора](contracts/emulator.openapi.yaml).

## Запуск

Нужны Docker с Compose v2 и доступом к интернету для первой загрузки образов и зависимостей. Локальные Java, Maven и Node для запуска в контейнерах не требуются. Все команды далее выполняются из корня проекта.

Задайте пароль новой БД и пароль демонстрационных пользователей в текущем терминале:

```sh
export APP_DB_PASSWORD='local-database-password'
export APP_COMMAND_PASSWORD='demo-password'
docker compose up -d --build --wait
```

Compose собирает и запускает все пять компонентов, применяет миграции и ждёт готовности. Первую инициализацию пользователей и адресов воркеров выполните один раз на пустой БД:

```sh
docker compose stop frontend backend
docker compose run --rm --no-deps -e APP_EXCHANGE_ENABLED=false backend \
  --server.port=0 --app.command=bootstrap \
  --app.worker-one-url=http://emulator:8090/workers/worker-1 \
  --app.worker-two-url=http://emulator:8090/workers/worker-2
docker compose up -d --wait
```

Повторять bootstrap на непустой БД нельзя: команда возвращает ошибку `AlreadyInitialized`, существующих пользователей и настройки не перезаписывает. Остановка backend на время служебной команды сохраняет общий лимит ресурсов. Демонстрационные задания создаются отдельно, при обычном запуске они не добавляются.

| Адрес | Что открывается |
|---|---|
| [localhost:5173](http://localhost:5173) | Интерфейс приложения |
| [localhost:8080/actuator/health](http://localhost:8080/actuator/health) | Готовность бэкенда |
| [localhost:8090/actuator/health](http://localhost:8090/actuator/health) | Готовность эмулятора |

Порты можно изменить до запуска через `FRONTEND_PORT`, `APP_PORT`, `EMULATOR_PORT`. Внутренние адреса контейнеров при этом сохраняются. Для локального HTTP используется `APP_SECURE_COOKIE=false`; при размещении за HTTPS задайте `true`.

Общий лимит пяти работающих контейнеров — **2 CPU / 3456 МиБ**: backend 0.75 CPU / 1536 МиБ, его БД 0.50 / 1024, emulator 0.25 / 512, его БД 0.25 / 256, frontend 0.25 / 128. Это лимиты работающего приложения; сборка образов, Docker, браузер и тестовый генератор требуют дополнительных ресурсов хоста.

### Пользователи

Все пользователи получают пароль `APP_COMMAND_PASSWORD`, указанный при bootstrap.

| Логин | Роль | Служба |
|---|---|---|
| initiator1, initiator2 | Инициатор | А |
| operator1, operator2 | Оператор | А |
| initiator3 | Инициатор | Б |

В службе Б оператора изначально нет: созданные там задания остаются новыми. Команда добавления оператора и подробности API — в [документации бэкенда](backend/README.md).

### Остановка и повторный запуск

```sh
docker compose ps
docker compose logs --tail=100 backend emulator frontend
docker compose down
docker compose up -d --wait
```

`down` сохраняет именованные тома: при следующем запуске сохраняются пользователи, задания, сессии и внешний реестр. Для существующего тома оставьте прежний `APP_DB_PASSWORD`: смена переменной не меняет пароль уже созданной БД. `docker compose down -v` удаляет БД проекта вместе со всеми данными; используйте её только для намеренного сброса своего экземпляра.

## Как проверить приложение вручную

1. Откройте интерфейс и войдите как `initiator1`. Создайте задание, например `Demo-1`, с любым из трёх типов. В карточке должен появиться назначенный оператор.
2. Выйдите и войдите под указанным оператором. Выберите воркер и отправьте задание.
3. Дождитесь результата: внешнее исполнение занимает 10–60 секунд, показ результата дополнительно зависит от опроса раз в 10 секунд. Проверьте историю и скачайте `.md`.
4. Примите результат. Состояние станет завершённым; изменение завершённого задания недоступно. Отрицательный результат тоже можно принять, файл в нём пустой.
5. Для проверки изоляции войдите как `initiator2` или `initiator3`: чужое задание не должно появиться в реестре и быть доступным по прямому адресу.

Для воспроизводимого отрицательного исхода до отправки новой операции:

```sh
sh emulator/emulatorctl configure worker-1 normal fail
```

После проверки верните обычный режим:

```sh
sh emulator/emulatorctl reset worker-1
sh emulator/emulatorctl reset worker-2
```

Другой адрес служебных команд задаётся через `EMULATOR_URL`, например `http://localhost:18090`. Все команды сбоев и независимая инспекция по внешнему ID — в [инструкции эмулятора](emulator/README.md). Настройки сбоев сохраняются после перезапуска, поэтому их нужно сбрасывать явно.

### Демонстрационные данные

После bootstrap на своём демонстрационном экземпляре:

```sh
export DEMO_PASSWORD="$APP_COMMAND_PASSWORD"
python3 backend/scripts/demo.py
```

Скрипт использует API приложения и настоящего эмулятора, создаёт шесть заданий разных состояний и записывает `backend/demo-report.json`. Нужен Python 3; адреса по умолчанию — порты 8080/8090, доступные параметры можно посмотреть через `python3 backend/scripts/demo.py --help`. Выполняющееся задание затем естественно завершится. Этот сценарий меняет данные и настройки указанного экземпляра; не запускайте его на окружении нагрузочной проверки.

## Автоматические тесты

Для локальных тестов нужны JDK 21, Maven 3.9+, Python 3, Node.js 22.12+ и pnpm 11.25.0. Для интеграционных и браузерных тестов нужен работающий Docker.

Подготовка фронтенда:

```sh
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend exec playwright install chromium
```

Быстрые проверки без БД:

```sh
python3 testing/run.py unit
```

Команда запускает проверку трассировки требований, unit-тесты backend и emulator, Vitest, TypeScript и unit-тесты генератора нагрузки. Сборка фронтенда отдельно: `pnpm --dir frontend build`.

Интеграционные проверки и совместный профиль:

```sh
python3 testing/run.py integration
```

Последовательно выполняются backend verify, emulator verify (также собирает jar) и backend `-Pjoint verify` с настоящим эмулятором. PostgreSQL создаётся фикстурами Testcontainers отдельно для каждого набора, параметры подключений передаются явно. Совместные сценарии проверяют потерю ответов, повтор через другого воркера, одно исполнение, дубликат и поздний ответ старой операции.

Браузерные сценарии:

```sh
python3 testing/run.py acceptance
```

Runner поднимает отдельный Compose-проект с новыми временными БД, проверяет реальные API и эмулятор на ширинах 390 и 1440 и удаляет тестовое окружение в `finally`. Эти тесты используют Vite; статическое Nginx-размещение проверяется отдельно командой `python3 testing/compose_follow_up.py`. При недоступности тестовой БД запуск прекращается: существующие БД и рабочий Compose не используются.

Отчёты: `backend/target/{surefire-reports,failsafe-reports,site/jacoco}`, `emulator/target/{surefire-reports,failsafe-reports,site/jacoco}`, `frontend/coverage` после `pnpm --dir frontend test:coverage`, `frontend/test-results` для Playwright. Критерии и отдельные команды — в [testing/README.md](testing/README.md).

## Нагрузочная проверка NF08

Выполняйте на отдельном пустом экземпляре. Создайте новое имя Compose-проекта, используйте свободные порты и запускайте все команды этого раздела в одном терминале. Не используйте имя уже существующего проекта.

```sh
export COMPOSE_PROJECT_NAME="tz-load-$(date +%Y%m%d%H%M%S)-$$"
export FRONTEND_PORT=15173
export APP_PORT=18080
export EMULATOR_PORT=18090
export APP_DB_PASSWORD='isolated-load-db-password'
export APP_COMMAND_PASSWORD='load-user-password'
docker compose up -d --build --wait
```

Выполните bootstrap из раздела запуска с тем же `COMPOSE_PROJECT_NAME`. Затем создайте 5000 заданий; демонабор на этом экземпляре не запускайте:

```sh
docker compose stop frontend backend
docker compose run --rm --no-deps -e APP_EXCHANGE_ENABLED=false backend \
  --server.port=0 --app.command=load-data --app.username=initiator1
docker compose up -d --wait
export LOAD_PASSWORD="$APP_COMMAND_PASSWORD"
export LOAD_OPERATOR_PASSWORD="$APP_COMMAND_PASSWORD"
python3 backend/load/profile.py \
  --url http://localhost:18080 \
  --emulator-url http://localhost:18090 \
  --environment 'Укажите CPU, RAM, ОС, Docker; пять контейнеров: 2 CPU / 3456 МиБ' \
  --output /tmp/tz-nf08-report.json
```

До прогона проверьте в реестре, что исходно ровно 5000 записей. Генератор работает вне лимита контейнеров: 20 последовательных клиентов с keep-alive, 30 секунд прогрева, 120 секунд измерений. Каждый клиент циклически выполняет список, карточку, создание и разрешённое изменение собственного задания. P95 чтения должен быть ≤2 с, изменения ≤3 с, ошибок — 0. Ошибки входят в отчёт, сбой порога завершает процесс ненулевым кодом. После нагрузки отдельная операция проверяет настоящие `finished_at` и `execution_count=1` через инспекцию эмулятора.

Генератор указывает бюджет пяти контейнеров: 2 CPU / 3456 МиБ. Поле `--environment` должно описывать реальную среду. Исторические измерения не являются результатом нового запуска.

После сохранения отчёта удалите только созданный нагрузочный экземпляр:

```sh
docker compose down -v --remove-orphans
```
