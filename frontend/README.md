# Фронтенд системы обмена

React, TypeScript в строгом режиме, Vite, React Router и TanStack Query. Приложение использует настоящий API; демонстрационных массивов и подмены сети в рабочей сборке нет.

## Общий запуск

Корневой `docker compose up -d --build --wait` запускает production-сборку фронтенда на http://localhost:5173 вместе с backend и emulator. Nginx проксирует `/api` и возвращает `index.html` для маршрутов приложения. Настройка пользователей и воркеров — в [общем README](../README.md). `API_TARGET` применяется только при локальной разработке с Vite.

## Установка и запуск

Требуются Node.js 22.12+ и pnpm 11.25.0.

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Адрес интерфейса: `http://127.0.0.1:5173`. Vite передаёт `/api` серверу `http://127.0.0.1:8080`, сохраняя единый origin для cookie сессии и CSRF. Другой адрес сервера задаётся только для процесса Vite:

```sh
API_TARGET=http://127.0.0.1:18080 pnpm dev
```

Запуск сервера, инициализация пользователей и настройка воркеров описаны в корневом README. Для входа доступны `initiator1`, `initiator2`, `operator1`, `operator2` первой службы и `initiator3` второй службы. Пароль задаётся при серверной инициализации; фронтенд его не хранит и не подставляет.

## Сборка и подключение

```sh
pnpm generate:api
pnpm typecheck
pnpm build
```

Типы `src/shared/api/schema.ts` генерируются из `../contracts/backend.openapi.yaml`. Генератор убирает комментарии из генерируемого исходника. Ручные копии DTO не используются. Генерацию следует повторять при согласованном изменении OpenAPI.

Сборка находится в `dist/`. Для размещения нужен сервер статических файлов с возвратом `index.html` для маршрутов `/tasks`, `/tasks/new`, `/tasks/:id`, `/problems` и проксированием `/api` на бэкенд. Параметры для общей конфигурации: команда сборки `pnpm build`, каталог `frontend/dist`, порт разработки `5173`, переменная `API_TARGET`. Корневая конфигурация запуска, сервер, эмулятор и контракты не изменяются фронтендом.

## Проверки

```sh
pnpm test
pnpm test:coverage
pnpm exec playwright install chromium
pnpm test:e2e
```

Unit- и компонентные тесты используют моки только на границе HTTP. Покрываются валидация и нормализация имени, границы описания, сессия, роли, серверные разрешения, фильтр и пагинация, версии, ключи действий, неподтверждённые ответы, сохранение без изменения полей, `fail`, UTC и безопасное скачивание, включая пустой файл.

Сквозной запуск `python3 scripts/test-e2e.py` создаёт новый Compose-проект с уникальным именем и двумя PostgreSQL в отдельных контейнерах с временным хранением. Порты API и эмулятора назначаются Docker. DSN заданы явно и не используют окружение разработчика. Базы не публикуются на хост. Скрипт инициализирует только это окружение и в `finally` удаляет его контейнеры и временные данные. Если Docker или тестовая БД недоступны, прогон прекращается без переключения на существующую БД.

Playwright проверяет реальные API и эмулятор на ширинах 390 и 1440: создание, выбор воркера, отправку, получение `fail`, скачивание, принятие; технически невалидный ответ, возврат, сохранение без правок и новую отправку; утерю результата и новую операцию через другого воркера. Навигация и кнопки проверяются клавиатурой. Для нативного списка воркеров проверяется достижимость фокуса через Tab, затем используется `selectOption`: автоматизация macOS не меняет выбор нативного списка от стрелок даже на чистом HTML. Полностью ручная проверка системного меню клавиатурой остаётся отдельной проверкой. Фактическое число исполнений проверяется через инспекцию эмулятора. Прямой запуск Playwright без переменных из изолированного окружения запрещён конфигурацией. При запуске артефакты ошибок и снимки создаются в `test-results/`.

## Устройство и поведение

- `app` — запуск, маршруты, сессия и настройки кэша.
- `pages` — реестр, создание и карточка.
- `features` — вход, формы, валидация и команды с ключами идемпотентности.
- `shared` — типы OpenAPI, HTTP, сообщения и представление времени/файлов.

Серверный кэш отделён от состояния форм. Чтение поддерживает отмену устаревших запросов; списки, карточка и история обновляются раз в 10 секунд. После команды обновляются связанные записи и история. Бизнес-состояния меняются только по подтверждённому ответу сервера.

При потере ответа кнопка повтора отправляет исходное тело и прежний ключ, даже если фоновое чтение уже получило новую версию. До ответа нельзя изменить тело этого запроса. Новое подтверждённое действие получает новый ключ. `retry` сохраняет серверную бизнес-операцию, а `send` после `LOST_RESULT` создаёт новую, как определено контрактом.

Редактируемая форма сохраняет исходную версию при фоновом обновлении. При конфликте введённые поля остаются видимы, повтор блокируется до явного обновления карточки. Обновление заново открывает форму с серверными значениями. Сохранение возвращённого задания не требует менять поля. После принятия результат и действия определяет сервер, редактирования нет.

Проблемы и материалы сверки доступны в карточке и истории. История сохраняет авторов, локальное время, обе стороны сверки и решения в том виде, в котором их возвращает сервер. Произвольные материалы показываются текстом, без исполнения HTML. Файл скачивается отдельным авторизованным запросом как `task-{id}.md`; Base64 из карточки не вставляется в DOM. Длительность остаётся целым числом секунд; моменты UTC отображаются в часовом поясе браузера с его названием.

Приёмочная матрица `../testing/frontend/TEST_PLAN.md` и её контракт не изменяются этой реализацией.

Для отдельных изолированных браузерных сценариев доступен фильтр:

```sh
python3 scripts/test-e2e.py --grep 'восстановление|исчерпания'
```

`--keep` сохраняет созданное этим запуском тестовое окружение для ручной проверки. Его уникальный Compose-проект и URL записываются в `test-environment.json`; после проверки выполните записанную команду Compose с аргументами `down -v --remove-orphans`. Без `--keep` очистка автоматическая. Этот режим не подключается к существующим БД.

## Повтор тестов на готовых образах

При недоступности реестра Docker допускается `python3 scripts/test-e2e.py --no-build --grep PATTERN` с явно заданными `TEST_BACKEND_IMAGE`, `TEST_EMULATOR_IMAGE` и `TEST_PROXY_IMAGE`. Образы должны соответствовать текущим runtime-исходникам. Runner создаёт новый Compose-проект с пустыми тестовыми БД; переиспользуются только образы. Без этих трёх переменных режим завершается ошибкой. Обычный запуск по-прежнему собирает образы.
