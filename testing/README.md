# Независимые критерии проверки

Исходные ожидания: development-spec.md, 04-system-integration.md, планы agent-tasks/*-plan.md и согласованные уточнения CLARIFICATIONS.md. Приложение и исходные планы не изменяются тестовым набором.

- [Бэкенд](backend/TEST_PLAN.md).
- [Эмулятор](emulator/TEST_PLAN.md).
- [Фронтенд](frontend/TEST_PLAN.md).
- [Задачи агентам](../agent-tasks/verification-follow-up.md).

`traceability.json` связывает ID теста, требования, задачи и исходник. Проверка ссылок выполняется командой `python3 -m unittest discover -s testing/tests`; это проверка метаданных, не доказательство корректности приложения.

Исполняемые тесты находятся в стандартных каталогах компонентов: backend/src/test, emulator/src/test, frontend/src и frontend/e2e. Они используют существующие фикстуры Mockito, управляемые часы, HTTP-моки и отдельные PostgreSQL Testcontainers. Дублирование фикстур в testing не требуется. В каждом testing/<направление>/tests/run.py есть переносимая обёртка быстрого прогона; нужны Maven/JDK 21 либо pnpm/Node.js. Ошибки инструментов не превращаются в успешные проверки.

## Порядок прогона

Из корня проекта:

```sh
python3 -m unittest discover -s testing/tests
mvn -f backend/pom.xml verify
mvn -f emulator/pom.xml verify
mvn -f backend/pom.xml -Pjoint verify
pnpm --dir frontend test
pnpm --dir frontend typecheck
pnpm --dir frontend test:e2e
python3 -m unittest discover -s backend/load -p 'test_*.py'
```

Emulator verify собирает jar для последующего joint-профиля. В unit-прогоне внешние сервисы подменяются только на границах компонента; совместный профиль использует реальный эмулятор. Браузерный runner создаёт уникальный Compose-проект с временными БД, задаёт подключения явно и удаляет окружение в finally. При ошибке запуска контейнера не переключаться на существующую БД.

Приёмочные сценарии не подменяются unit-тестами: таблицы связывают существующие проверки с требованиями; частичные связи не означают полного покрытия. Успешные старые отчёты не считаются текущим запуском. Производительность проверяется отдельно; unit-тесты генератора нагрузки не доказывают соблюдение P95.

Общий запуск: `python3 testing/run.py unit`, `python3 testing/run.py integration`, `python3 testing/run.py acceptance`. Первый сбой останавливает выбранный набор с ненулевым кодом. Runner не запускает общий рабочий compose.yaml, не считывает DSN из пользовательских конфигов и не выбирает существующую БД при ошибке Docker.

## Общая конфигурация и нагрузка

`python3 testing/compose_follow_up.py` проверяет production-статику, SPA и API через Nginx, сессию/CSRF, реальное внешнее исполнение и сохранность после перезапуска пяти контейнеров. Каждый запуск создаёт уникальные сеть и именованные тома; в конце удаляются только его ресурсы.

`python3 testing/compose_follow_up.py --load` создаёт отдельное пустое окружение, выполняет bootstrap и load-data, проверяет 5000 исходных записей и запускает NF08. На время измерения остальные тестовые прогоны должны быть завершены. При запуске каталог `testing/verification` создаётся автоматически; исходные измерения и сведения о среде сохраняются отдельными JSON, предыдущие отчёты не перезаписываются.

`--inspect-isolation` показывает имена новых сети и томов без запуска контейнеров. Все режимы требуют доступного Docker; при ошибке используется ненулевой код завершения без переключения БД.

При недоступности реестра образов `--image-project <имя>` использует уже собранные образы трёх приложений указанного Compose-проекта. Перед запуском требуется проверить их соответствие текущим продуктовым исходникам. Идентификаторы и даты образов сохраняются в отчёте; сеть, контейнеры и тома создаются заново.
