# Спецификация разработки системы обмена

Версия 1.0 от 13 ноября 2026 года. Статус: согласовано для разработки.

Источник: `04-system-integration.md`, версия 2.1. Все обязательные требования источника сохраняются. Бизнес-правила и технические решения согласованы с заказчиком.

## 1. Границы и стек

Веб-приложение принимает задания, направляет их внешнему эмулятору, получает результаты и поддерживает восстановление и сверку. Реальные внешние системы, пакетная отправка и промышленное развёртывание не входят в MVP.

Стек: Java и Spring, React и TypeScript, PostgreSQL. Эмулятор имеет собственное постоянное состояние, несколько воркеров с разными эндпоинтами и общее хранилище ключей идемпотентности.

## 2. Согласованные роли и доступ

- Пользователь принадлежит службе. Между службами доступ запрещён.
- Инициатор создаёт задания и видит только свои задания, их историю и результаты.
- Оператор видит задания своей службы, изменяет только назначенные ему.
- Каждое задание создаётся в статусе «Новое». Система автоматически назначает оператора этой службы с минимальным числом незавершённых заданий; назначение переводит задание в статус «Ожидает отправки». При равенстве выбирается минимальный ID оператора. Если в службе нет оператора, задание сохраняется в статусе «Новое» без назначения. При создании оператора задания этой службы автоматически назначаются по правилу минимальной нагрузки.
- Возвращённые инициатору задания продолжают учитываться в нагрузке оператора. Завершённые исключаются.
- Проверки роли, службы, автора и назначенного оператора выполняются сервером для каждого API, включая историю и скачивание файла.

## 3. Задание и жизненный цикл

Задание содержит неизменяемое после создания имя длиной от 1 до 100 символов, описание от 0 до 1000 символов и тип `process`, `research` или `collect`.

Черновиков нет. Создание всегда сохраняет задание в статусе «Новое». Последующее автоматическое назначение оператора переводит его в «Ожидает отправки», но не отправляет эмулятору. Если оператора нет, задание остаётся в статусе «Новое». Инициатор может менять описание и тип до отправки оператором либо после возврата оператором из-за технически невалидного результата.

Оператор выбирает воркера и отправляет задание. Назначение воркера не входит в тело сообщения: запрос направляется на его эндпоинт. После отправки смена воркера допускается при недоступности исполнителя.

Корректный результат со статусом `success` или `fail` передаётся оператору на принятие. Отрицательный бизнес-результат является полноценным результатом и не служит основанием для возврата на исправление. После принятия результата оператором задание фиксируется и не редактируется.

Технически невалидный результат выделяется как проблема. Оператор может повторить ту же операцию с прежним ключом без нового исполнения либо вернуть задание инициатору. Нажатие «Сохранить» инициатором автоматически возвращает задание прежнему оператору, в том числе без изменения полей. Следующая отправка создаёт новую бизнес-операцию и новый ключ; прежняя операция и история сохраняются.

Срока и просрочки нет. Измеряется только длительность исполнения воркером, передаваемая в `processing_time`.

### Названия бизнес-состояний

| Состояние | Смысл |
| --- | --- |
| Новое | Начальный статус каждого задания; ожидает назначения оператора |
| Ожидает отправки | Оператор назначен либо задание сохранено инициатором после возврата; ожидает отправки оператором |
| На исполнении | Отправка инициирована, готовый валидный результат ещё не принят локально |
| Ожидает принятия | Получен валидный результат `success` или `fail` |
| Возвращено инициатору | Оператор разрешил исправление после невалидного результата |
| Завершено | Оператор принял результат; задание зафиксировано |

Состояние обмена хранится отдельно: ожидает доставки, доставляется, получение подтверждено, исход доставки неизвестен, ожидает повтора, требуется разбор. Бизнес-ошибка `fail` не является ошибкой доставки.

## 4. Контракт обмена

### Согласованная семантика

Приложение генерирует постоянный ключ бизнес-операции. Повтор отправки с тем же ключом, в том числе другому воркеру, не создаёт нового исполнения. Эмулятор возвращает ID принятого задания; по этому ID приложение получает результат.

Готовый результат содержит:

| Поле | Значение |
| --- | --- |
| `id` | ID задания, возвращённый эмулятором при приёме |
| `status` | `success` или `fail` |
| `processing_time` | Целое число секунд исполнения воркером |
| `data` | Base64-представление содержимого файла |

Результат скачивается с расширением `.md`. Эмулятор формирует произвольный текст Lorem Ipsum. Максимальный размер декодированного файла — 102 400 байт. Время исполнения передаётся вместе с готовым результатом, не при приёме задания. Каждая новая бизнес-операция исполняется воркером в реальном времени в течение случайно выбранного интервала от 10 до 60 секунд. POST подтверждает приём без ожидания завершения исполнения; до готовности результата GET возвращает `202`. Повтор той же операции не запускает исполнение и отсчёт времени заново. `processing_time` отражает фактическую длительность исполнения.

### HTTP-контракт

- `POST {worker_endpoint}/operations`: ключ в `Idempotency-Key`, тело содержит `name`, `description`, `type`; ответ `202` с `id`.
- Повтор с прежним ключом и тем же содержимым возвращает прежний ID. Изменённое содержимое с прежним ключом отклоняется с `409`.
- `GET {worker_endpoint}/operations/{id}`: `202`, пока результата нет; `200` с готовым результатом; `404`, если операция неизвестна.
- Все воркеры читают общий реестр операций. Выбор нового эндпоинта не создаёт новую операцию с прежним ключом.
- Служебный API эмулятора позволяет независимо проверить состояние, сохранённый результат и счётчик исполнений, а также включить воспроизводимый сбой.

Невалидный JSON, неизвестный статус, несоответствующий ID, отрицательная или нецелая длительность, некорректный Base64 и превышение размера результата требуют разбора. Ошибки контракта не приводят к автоматическому принятию результата.

## 5. Архитектура и хранение

Сервер приложения, фоновый обработчик обмена, PostgreSQL и отдельный эмулятор. Фоновый обработчик может работать в процессе сервера. Внешние запросы не удерживают транзакцию пользовательского API.

Сохранение бизнес-изменения, аудита и задания на обмен выполняется одной транзакцией. Обработчик читает постоянную очередь из БД. После перезапуска продолжает незавершённую работу. Захват операции ограничен сроком, чтобы аварийно прерванная обработка могла продолжиться.

Сущности:

| Сущность                 | Назначение                                                            |
|--------------------------|-----------------------------------------------------------------------|
| Служба, пользователь     | Принадлежность, роль и демонстрационный вход                          |
| Задание                  | Автор, оператор, поля задания, бизнес-состояние, версия               |
| Бизнес-операция          | Ключ, снимок отправляемых полей, воркер, внешний ID, состояние обмена |
| Задание обмена           | Вид действия, время следующей попытки, счётчик, захват обработчиком   |
| Попытка обмена           | Начало, окончание, исход, диагностические сведения                    |
| Результат                | Внешний ID, статус, длительность, файл и связь с операцией            |
| Проблема и сверка        | Локальное и внешнее наблюдения, расхождение, решение оператора        |
| Аудит                    | Автор, время, объект, действие и изменение                            |
| Идемпотентный запрос API | Ключ действия, пользователь, отпечаток запроса, сохранённый ответ     |

Эмулятор хранит свои операции, ключи, результаты, счётчики исполнения и настройки сбоев отдельно от состояния приложения.

Ограничения БД обеспечивают уникальность ключей и связность сущностей. Конкурирующее редактирование проверяет версию задания. Отправка одновременно с редактированием не должна приводить к незаметной потере изменения или отправке несогласованного снимка. Назначение оператора сериализуется внутри службы, чтобы параллельные создания не обходили правило нагрузки.

## 6. Идемпотентность и применимость результатов

- Повторы одного пользовательского действия через UI или API не создают второе задание или вторую бизнес-операцию; независимые действия имеют разные ключи.
- Ключ внешней операции сохраняется до первого сетевого обращения.
- Потеря ответа не означает, что исполнения не было. Неопределённость видна оператору; повтор использует прежний ключ.
- Дубликат результата не создаёт повторного эффекта.
- Результат применим только к соответствующей операции и внешнему ID. Поздний результат прежней операции не заменяет результат новой.
- Несовпадающие результаты одной операции фиксируются как расхождение и не перезаписываются молча.
- История прежних операций сохраняется после исправления и повторной отправки задания.
- Эмулятор атомарно распознаёт ключ и регистрирует исполнение. Перезапуск и конкурентные запросы через разные воркеры не увеличивают число исполнений одной операции выше одного.

## 7. Повторы и таймауты

Согласованные параметры обмена:

| Параметр | Значение |
| --- | --- |
| Таймаут соединения | 3 секунды |
| Общий таймаут внешнего запроса | 5 секунд |
| Автоматические повторы временно неуспешного запроса | 5 повторов после первой попытки |
| Задержки повторов | Базовые 5, 15, 30, 60, 120 секунд; к каждой задержке добавляется случайное число от 2 до 5 секунд |
| Опрос ещё выполняющейся операции | Раз в 10 секунд |
| После исчерпания повторов | Проблема для оператора, автоматические повторы остановлены |
| Ручной повтор | Новый ограниченный цикл попыток той же операции |

Сетевые ошибки, таймауты и HTTP `5xx` считаются временными. Невалидный ответ и конфликт содержимого ключа требуют разбора. Ответ «ещё выполняется» не расходует бюджет ошибок. Завершение, возврат или замена активной операции прекращают её обычный опрос. Исчерпание повторов не удаляет сохранённую операцию.

## 8. Сверка и решения оператора

Сверка сравнивает локальную операцию с фактическим состоянием эмулятора по ключу и внешнему ID. Результат сверки сохраняет время и обе стороны сравнения. Сверка запускается вручную и автоматически после неоднозначной доставки. Если после потери ответа внешний ID неизвестен, приложение повторяет POST с прежним ключом, получает существующий ID и затем запрашивает результат. Отдельный поиск по ключу не используется.

Допустимые согласованные действия: принять подтверждённый внешний результат, повторить доставку той же операции, назначить или сменить исполнителя в разрешённых случаях. Технически невалидный результат также допускает возврат инициатору.

Неустранённая проблема остаётся видимой до решения; отдельная кнопка «Оставить открытой» не нужна. Решение оператора и его эффект записываются в историю. Автоматическая сверка сама не принимает результат за оператора.

## 9. API приложения

| Метод и путь | Действие |
| --- | --- |
| `POST /api/session`, `DELETE /api/session`, `GET /api/me` | Вход, выход, текущий пользователь |
| `GET /api/tasks` | Реестр с фильтром по типу и пагинацией |
| `POST /api/tasks` | Создание и назначение оператора |
| `GET /api/tasks/{id}` | Карточка |
| `PATCH /api/tasks/{id}` | Изменение описания и типа инициатором |
| `PUT /api/tasks/{id}/worker` | Выбор допустимого исполнителя оператором |
| `POST /api/tasks/{id}/send` | Отправка оператором |
| `POST /api/tasks/{id}/retry` | Допустимый повтор |
| `POST /api/tasks/{id}/return` | Возврат инициатору |
| `POST /api/tasks/{id}/accept` | Принятие результата и завершение |
| `POST /api/tasks/{id}/reconcile` | Запуск сверки |
| `GET /api/tasks/{id}/history` | История и попытки обмена |
| `GET /api/tasks/{id}/result/file` | Скачивание результата |
| `GET /api/problems` | Проблемы в доступной области |

Изменения проверяют права, состояние и ожидаемую версию. Создание и команды с бизнес-эффектом защищаются ключом идемпотентности. Схемы запросов и ошибок должны быть отражены в документации API при реализации.

## 10. Интерфейс и время

Обязательны реестр, форма создания, карточка, история обмена, список проблем и результаты сверки. Карточка отдельно показывает бизнес-состояние, доставку, оператора, воркера и результат. Доступные действия определяются серверными правами и состоянием.

Файл скачивается как `.md`; произвольное содержимое результата не исполняется в браузере. Интерфейс поддерживает ширину 390–1440 пикселей, клавиатуру, подписи, понятные ошибки, пустые состояния и выполнение запросов.

Моменты времени хранятся в UTC и передаются API с явным обозначением UTC. Интерфейс переводит их в часовой пояс браузера и показывает используемый пояс. `processing_time` — длительность, она не переводится между поясами. Просрочка и календарные сроки отсутствуют.

## 11. Демонстрация и проверка

Демонстрационный набор содержит две службы. В первой — два инициатора и два оператора. Во второй — инициатор без оператора для проверки статуса «Новое» и последующего автоматического назначения при создании оператора.

Шесть заданий: новое во второй службе, ожидающее отправки, выполняющееся, с успешным результатом, с отрицательным результатом и возвращённое инициатору.

Эмулятор воспроизводит недоступность, потерю ответа после исполнения, дубликат и задержанный результат. Состояние и число исполнений проверяются независимо от приложения. Дубликат демонстрируется повторной обработкой одного ответа. Задержанный результат воспроизводится удержанием ответа старой операции до появления новой. Управление выполняется служебными командами эмулятора.

Критерии приёмки:

- Создание при недоступном эмуляторе сохраняется после перезапуска приложения и БД; обмен продолжается после восстановления (D01, D04, D-NF01, NF03).
- Повтор после потери ответа, в том числе через другой воркер, даёт ровно одно исполнение (D02, D03, D07, D-NF02).
- Дубликат результата не меняет бизнес-эффект; поздний результат прежней операции не откатывает состояние (D03, D-NF02).
- Технически невалидный ответ создаёт проблему; исправление инициатором возвращает прежнему оператору, следующая отправка получает новый ключ (D04, D06).
- `fail` доступен для принятия как результат, после принятия редактирование запрещено (D01, D06).
- Сверка сохраняет расхождение и решение оператора (D05, D-NF03).
- Прямые запросы не обходят службу, авторство и назначение оператора (NF02).
- Параллельные изменения и повтор команды не создают потерянных изменений и повторных действий (NF03, NF04, NF10).
- История сохраняет автора, время и изменения после перезапусков (NF05).
- Основной сценарий проходит на обеих граничных ширинах и с клавиатуры (NF06).

Часть автоматических проверок использует PostgreSQL только в отдельном тестовом Docker-контейнере. Существующие БД и fallback на их подключения запрещены. При невозможности запуска контейнера тесты останавливаются и передаются пользователю для самостоятельного прогона.

## 12. Нагрузка и запуск

Отдельная команда создаёт 5000 заданий и необходимые связи. Профиль: 30 секунд прогрева, 120 секунд измерений, 20 последовательных клиентов, равные доли списка с фильтром по типу и страницей 20 записей, карточки, создания и разрешённого изменения описания/типа. Для изменений подготавливаются принадлежащие инициаторам задания до отправки.

P95 чтения — не более 2 секунд, изменения — не более 3 секунд. Указываются успешные запросы, ошибки и причины; ошибки не исключаются молча. Сервер, PostgreSQL и эмулятор суммарно ограничены 2 логическими CPU и 4 ГиБ RAM; генератор и браузер вне лимита. Эмулятор работает без искусственных сбоев. Отдельно показывается время от локального принятия до внешнего исполнения, которое не заменяет ни API latency, ни `processing_time`.

README должен содержать воспроизводимый запуск, миграции, демонстрационные учётные записи, команды сбоев, проверок и нагрузочного прогона, параметры среды, ограничения ресурсов, устройство системы и согласованные допущения. Платные внешние сервисы не требуются. Технические журналы не содержат паролей и ключей доступа.

## 13. Статус согласования

Состояния, контракт обмена, API, архитектура, хранение, параметры повторов, восстановление внешнего ID, сценарии сбоев и демонстрационный набор согласованы. Новые неоднозначности при реализации выносятся на обсуждение, а не разрешаются молчаливыми допущениями.
